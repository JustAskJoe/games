Summary

Build Tilebound in TypeScript. The game rules are a pure engine with no graphics. The look is illustrated 2D in a vintage 1920s Art Nouveau mahjong-set style with a light touch of folk magic, drawn with Phaser and bundled with Vite, because layered 2D art is the cheapest look to make well, runs on any phone and stays crisp on iPad (one tile frame with swappable critter and finish layers, portrait paint-overs, painted town backdrops). The launch target is iPad and phone (wrapped with Capacitor) as a single-player game, free to try with a one-time unlock, followed by PC on Steam and a mixed-reality table on PICO, built and tested with PICO CLI. The rules follow American mahjong: a House Card of target hands, the Swap before each hand, and Mimics as jokers.

Why this stack:

  • AI coding tools write TypeScript very well, and a rules engine with no graphics can be fully tested and simulated.

  • A web build means a playtester only needs a link.

  • Keeping the engine separate from the renderer means it could move to Godot later without rewriting the rules.

The pipeline revolves around one loop: change a rule or tile in data → run 10,000 bot games → check the numbers → playtest.

The first real milestone is the single-player vertical slice: pick a starter, Kettle Cove (tutorial and the club), Route 1, the first parlor master in Cinder Quay, then a first Mahj Night. The game stays single-player with no servers to run; online play with friends is a possible later update.

Stack choice

TypeScript + Phaser wins for the jam and the vertical slice. Godot is the fallback if console ports become the priority.

Update, Oct 16: after trying pixel art and stylized 3D, the art direction is settled on illustrated 2D: vintage Art Nouveau mahjong-set styling with a light touch of folk magic. That puts Phaser back as the client for the jam, slice and launch, and drops Babylon.js. It keeps TypeScript and the web playtest link. The XR table uses WebSpatial (HTML and React), which PICO CLI supports: the painted tiles and character portraits become flat panels standing on your real table. The rules engine doesn't change. Gate after the slice: if the art pipeline or older phones fall short, move the client to Unity 2D. Tonight's prototype stays a flat table with placeholder tiles, because the rules come first.

What we keep no matter which engine wins:

  • Rules engine in pure TypeScript. No rendering, no clock, no random calls except a seeded RNG. Every table seats four (master matches, casual tables, Mahj Night); the early tutorial lessons use two seats with the same rules switched down. The app, the club server, the bots and the tests all call the same functions.

  • Content as data. Tiles, House Cards, parlors, opponents and dialogue live in JSON files, so changing balance never means a code change.

  • Layered 2D art that scales cleanly. Paint at 2× the largest target (iPad Pro) and export sprite atlases at two sizes; the layout stretches to fit tablet and phone shapes. A tile is three layers (frame, critter painting, finish overlay), so a new tile set is a new frame and finish, not 34 new paintings.

Architecture

The renderer, the bots and the tests all call the same rules engine, so a rule fixed once is fixed everywhere.

Folder layout: src/engine (rules), src/content (JSON plus schemas), src/game (Phaser scenes: Title, Overworld, Duel, Bag, Wall Editor), sim/ (bot runner) and tools/ (scripts that export art and validate data).

Data model

Everything a designer would tweak is a JSON record, checked against a schema when the game loads (Zod works well for this). These are the three records the vertical slice needs.

Tile — one record for each of the 34 types:

{
  "id": "ember-2",
  "suit": "ember",
  "rank": 2,
  "name": "Cindermole",
  "stage": 1,
  "ability": { "trigger": "onMeld", "effect": "burnWall", "amount": 1 },
  "sprite": "tiles/ember-2",
  "variants": ["plain", "carved", "jade", "gilded"]
}

Parlor — a location that has a house rule, a bag and opponents:

{
  "id": "ember-noodle-bar",
  "town": "cinder-quay",
  "houseCard": [
    { "name": "Kettle Kick", "pattern": "E111 E222 E3333 E4444", "points": 25 },
    { "name": "Three Friends", "pattern": "E5555 T5555 G5555 NN", "points": 30 }
  ],
  "bag": { "size": 6, "weights": { "ember": 0.5, "tide": 0.2, "grove": 0.2, "honor": 0.1 } },
  "regulars": ["noodle-cook", "dock-kid", "line-chef"],
  "master": "old-mags"
}

Opponent — a wall list plus AI weights, so each personality is just data:

{
  "id": "old-mags",
  "wall": "walls/old-mags.json",
  "ai": { "aggression": 0.8, "callRate": 0.6, "readyEagerness": 0.9, "blunder": 0.05 },
  "intro": "dialogue/old-mags-intro"
}

The save file stores your collection, your walls, beaten opponents and your current map, all versioned so later updates can migrate old saves.

Opponent AI, balance and the tutorial helper

One piece of math drives three features: the opponents, the balance bots and the beginner hints. That math is "tiles away", the minimum number of tile swaps a hand needs before it can declare Ready. Mahjong players call it shanten.

  • Opponent AI. On each discard, the AI scores every tile in its hand by how much throwing it away hurts its tiles-away count. It then shifts those scores by its personality weights (aggression, how often it calls, how eager it is to declare Ready, and a deliberate blunder rate). Easy opponents blunder more. Masters almost never blunder and lean hard into their house style.

  • Beginner hints. The same calculation powers the player's helpers: a "2 tiles from Ready" counter, a glow on tiles that already belong to a possible meld, and an optional suggested discard. Players who don't know mahjong learn by watching the counter go down. Every helper can be switched off in settings.

  • Balance bots. Running npm run sim plays thousands of four-bot games with no graphics and prints a report. Every balance change has to pass these checks:

MetricTarget
Rounds per hand12–18
Hand length8–12 minutes for a human
Dealer (East) win rate25% ± 3
Wins by each card hand4–30% each
Hands won by an honor-tile setunder 15%
Wall games (nobody wins)under 25%

These targets are design guesses. Adjust them after the first human playtests.

Production pipeline

Every change follows the same five steps, and step 2 is a gate: if the bots miss a target, the change goes back to design before anyone draws art for it.

The four tracks inside that loop:

  • Content. Designers edit a tile and opponent sheet, a script converts it to JSON, and Zod rejects any bad row at build time. Dialogue is written in plain text files, one per character. AI drafts first passes; a person edits every line.

  • Art. Illustrated in Procreate or Photoshop: one layered file per critter, per character and per tile finish (plain, carved, jade, gilded). AI is used for mood and early sketches only; artists paint every final asset. A script (TexturePacker or free-tex-packer) builds sprite atlases plus JSON that Phaser loads directly. Palette: plum, cream and gold leaf, with ember, tide and grove reserved for the suits.

  • Audio. Lo-fi music with warm keys, soft drums and a touch of 1920s parlor jazz: one theme per town, a gentle duel loop and a big master track, exported as OGG. Tile sounds (the clack, the shuffle, a set laid down) are recorded from real sets, with a slightly different sound per finish.

  • Build. Every push to main runs the tests and a 1,000-duel sim; if both pass, GitHub Actions builds the game and uploads it to a private itch.io page. Playtesters always have the latest link.

Platforms and shipping

One codebase, wrapped differently for each store. The audience plays on tablets and phones, so mobile leads. Ship them in this order:

  1. Web link for the jam and every playtest.

  2. iPad and phone (iOS, Android) for the slice and the launch, wrapped with Capacitor. TestFlight for slice playtests. Landscape on tablets; on phones the hand runs along the bottom.

  3. Online play, maybe later: out of scope for launch. Saves use local storage plus iCloud / Google Play sync, so there are no servers to run. Because the rules engine is headless, a game server could run it later if online play with friends ever makes sense.

  4. Steam (PC, Steam Deck) from the same build in an Electron wrapper, once mobile is live.

  5. XR table on PICO. Tiles on your real table, club friends seated around it. PICO CLI 0.5.0 (released Sept 15, 2026) lets Claude Code create, build, run and debug spatial apps for PICO OS 6 and Space Pro, in the emulator or on a device, with logs and profiling. It supports web-based spatial apps (WebSpatial: HTML and React), which fits our TypeScript code; native Spatial SDK and Unity are its other routes.

The save format and the seeded RNG are shared across every platform, so a daily puzzle hand is the same everywhere and a cloud save works on any device.

Milestones

Tonight's goal is small: a paper duel and an engine whose bot sim prints turns per hand. Everything after that is gated by real players, not by a calendar.

Durations are estimates for part-time, AI-assisted work.

The vertical slice:

  1. Pick your starter. On the ferry dock, choose Cindermole (Ember), Reedling (Tide) or Mossmouse (Grove). Each comes with a starter wall.

  2. Kettle Cove = the tutorial and the club. Your neighbor Bev teaches with hands that grow: 5 tiles, then 8 with the first House Card. You join the Tile & Teacup club and meet Lena.

  3. Route 1. Wild tiles you catch with quick puzzle hands, plus three travelers. The Swap and calls are taught here at 11 tiles.

  4. Cinder Quay and Old Mags. The full 14-tile game with Mimics, then the master duel. Winning gives the Copper Ladle badge.

  5. Mahj Night. Back at the club, a four-seat table with Bev, Lena and a bot.

Tutorial principles for players who don't know mahjong: every rule arrives inside a duel that needs it, the "tiles from Ready" counter is always visible, a hint button suggests a discard, and the screen uses plain words (the Swap, Set of three, Mimic, Mahj!). Club players can tap "I know mahjong" to skip straight to full hands and switch the screen back to table words.

Risks

The biggest risk is design, not tech: whether a four-seat table is fun and followable for someone who has never played mahjong. The full rules are in the Tilebound: Prototype Rules Sheet.
